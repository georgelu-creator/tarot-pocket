# Tarot Pocket 跨端演进方案

更新：2026-09-23。本文记录 Web、微信小程序与 iOS 的复用边界；它是架构决定，不是已经完成小程序或 App Store 上架的声明。

## 当前决定

本轮不重写现有 Web 应用。先把最有价值、也最适合复用的部分保持为不依赖 DOM 的 JavaScript：

- 78 张牌与来源、牌阵和场景目录；
- 洗牌后的牌序、正逆位、选牌和存档结构；
- 基于牌阵的本地解读；
- 学习课程、题库、答题判断和牌义资料；
- AI 请求结构、错误类型和匿名事件字典。

浏览器页面只负责排版、手势、导航和可访问性。以后的小程序和 iOS 壳分别接入存储、网络、分享、生命周期与安全区适配器，不能复制一套新的牌义和判断规则。

## 推荐路线

| 阶段 | 方案 | 复用内容 | 验收边界 |
|---|---|---|---|
| 现在 | 保持 PWA/静态 Web；新增核心纯函数模块 | 全部现有内容、存档和本地解读 | 先完成手机网页真实体验 |
| 微信小程序原型 | 用 Taro 建 UI 壳，导入相同内容与核心模块 | 牌库、牌阵、本地解读、课程、请求协议 | 先做首页→三牌→本地结果、学一张牌两条闭环；不先搬完整页面 |
| iOS 原型 | 用 Capacitor 包装 Web 作为低成本验证；若原生交互或审核需要，再把核心模块接入 React Native/Taro RN 壳 | 先最大化复用现有 Web 和离线资源 | 必须有离线学习、恢复、通知/小组件等真实 App 价值，不能只提交网站外壳 |

Taro 的官方定位是以 React 语法编译到微信小程序、H5 等多端；Capacitor 的官方定位是把现有 Web 应用接入 iOS/Android 原生运行时。两者解决的问题不同，因此不为了“一个框架”强行重写已经工作的 Web。参考：[Taro 官方文档](https://docs.taro.zone/docs/)、[Capacitor 官方文档](https://capacitorjs.com/docs)。

Apple 审核 4.2 要求应用具备足够的功能和长期价值，简单重新包装网站存在被拒风险。iOS 立项时至少验证完整离线学习、可靠恢复、原生通知或小组件、系统分享与无障碍，不把网页能打开当成上架完成。参考：[Apple App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)。

## 必须保持的接口

1. 核心模块不得读取 `document`、`localStorage` 或平台全局；依赖通过参数传入。
2. 三个既有存储键和版本 1 备份继续可读；跨端导入导出使用同一公开数据结构。
3. 平台适配器只保存业务数据，不保存供应商密钥；AI 密钥始终在服务端。
4. 牌阵位置用稳定 `positionId`，界面坐标另存为展示配置；更换端不能改牌义。
5. 统计事件使用同一白名单；小程序和 App 也不发送问题正文、抽牌组合、答案或学习记录。
6. 每个端分别验证键盘、安全区、返回、后台恢复、离线、网络失败和减少动态；Web 测试不能代替真机。

## 迁移前置检查

- 核心模块在 Node 中可运行，并有固定输入输出测试；
- UI 不直接修改牌阵或课程定义；
- 所有图片许可、双语内容和来源清单能随端打包；
- 服务端允许精确的小程序/App来源或平台签名，不使用通配来源；
- 发布、商店审核、微信主体认证、隐私说明和真实设备测试分别留证。
